From Manual QA to Test Automation

Six-plus years, four kinds of products, and the skills that actually carried over.

I didn't plan a career in testing. I studied computer science at NTU, did an internship writing microcontroller software, and my first full-time job was in database support: backups, migrations, upgrades, and a lot of "why doesn't this report match what I expected?"

Looking back, that last question is basically what testing is.

What manual testing taught me

Two years of testing real user flows by hand on three platforms was not wasted time. It's where I learned to read a requirement and ask "what happens if…?" before anyone writes code. Good automation starts from good test cases, and good test cases come from having clicked through the product yourself.

The jump to automation

My first Pytest scripts were rough: hard-coded data, long tests that checked ten things at once, and no idea why they failed on CI but passed on my laptop. What helped most:

  • Own the test data. Create what a test needs through an API before it runs, and clean it up afterwards. Most of my early flakiness was tests depending on data someone else had changed.
  • One behaviour per test. When a test fails, its name should already tell you what broke.
  • Run everything in CI. A suite that only runs on one person's machine isn't really a suite. Automatic retries help with genuinely flaky infrastructure, but they shouldn't hide real bugs.
  • API tests before UI tests. They're faster, far less flaky, and catch most of the same bugs.

If you're starting out

  1. Learn Python properly, not just enough to copy a Selenium example.
  2. Learn HTTP and how to test an API with plain requests and Pytest. It pays off more than any UI framework.
  3. Learn enough SQL to check what the application actually saved.
  4. Keep your manual-testing instincts. Automation is how you repeat a good test, not how you think of one.
